### BLK-03: India DLT Registration & Transactional SMS Gateway
- **Severity**: **HIGH** (Production Blocker for Real Customer/Driver Logins)
- **Root Cause**: Telecom Regulatory Authority of India (TRAI) mandates Distributed Ledger Technology (DLT) registration for sending transactional SMS OTPs. Without registered Entity ID, Sender Header (e.g., `NABINM`), and approved template IDs, SMS gateways will reject OTP dispatches in production mode.
- **Affected Artifacts**: Customer Login, Driver Login, Merchant Verification, Trip Start OTPs.
- **Measured consequence of this absence, 2026-10-12**: chain link 12 `test_phase7_security.js` died with `Fatal error running Phase 7 security suite: Error: OTP generated but SMS delivery failed: SMS_PROVIDER is not configured… { code: 'SMS_GATEWAY_NOT_CONFIGURED', status: 503 }` (`src/services/SmsGatewayService.js:279-287`, re-anchored from `:264-272` after `#286` inserted the CONSOLE refusal above it; reached from `src/database.js:6551`, re-anchored from `:6552` after `#288` put the dispatch's result to work below it), and chain link 8's AUTH-10 child crashed for the same reason. Both suites were rewritten to measure the code decision without needing delivery (they now pass: 48/0 and 22/0 — link 8 at 16 when AUTH-18 was added, 22 since F-10's AUTH-19…AUTH-24), which leaves exactly one thing this blocker still denies: **no check anywhere can prove a real OTP was dispatched to a handset**, and the production branches that require delivery remain unexecutable here. The refusals themselves are correct behaviour — production must not simulate SMS — so this is a credential gap, not a code gap.
- **Mock door closed at the root, 2026-10-12 (`#286`, was evidence finding F-2)**: production would previously accept an explicit `SMS_PROVIDER=CONSOLE` and answer `delivered: true` (`src/services/SmsGatewayService.js:92`) without dispatching anything — the one place where the directive's absolute "never allow mock … OTP adapters to run in production" could be bypassed by an operator's env var. `:269-277` now refuses it with 503 `SMS_MOCK_PROVIDER_FORBIDDEN` before any adapter is chosen. Measured **27/3 RED → 32/0 GREEN** in `sms_gateway_test.js` (hermetic) and **16/0** in chain link 8, whose new AUTH-18 runs `sendAuthOtp` in a production process and requires the refusal; links 12 and 66 are unmoved (48/0, 20/0). BLK-03 stays **OPEN** regardless — a refusal is not a delivery, and the credentials this blocker asks for are still what decides whether an OTP reaches a handset.
- **The trail now says what happened, in order (2026-10-12, `#288`, was evidence finding F-10)**: the audit row was written *before* `SmsGatewayService.dispatch` was called and worded as though the send had succeeded, so every send this blocker refuses — no provider configured, the CONSOLE mock refused in production, a 502 from the gateway — left a security record asserting `AUTH_OTP_DISPATCHED` with `success: true` for a code no handset ever saw, and no record of the refusal at all. `src/database.js:6516-6615` now writes `AUTH_OTP_REQUESTED` when the challenge exists, `AUTH_OTP_DISPATCH_FAILED` (`success: false`, `failure_reason` carrying the gateway's own code) when the dispatch throws, and `AUTH_OTP_DISPATCHED` only after the gateway returns a receipt, whose `provider` and `messageId` go into `metadata`. Measured **18 PASSED / 4 FAILED RED → 22 PASSED / 0 FAILED GREEN** in chain link 8 (new checks AUTH-19…AUTH-24 drive the real gateway boundary rather than a stub, and pin that the minted code never reaches the trail); links 12, 66 and `sms_gateway_test.js` are unmoved (48/0, 20/0, 32/0). Durable rows were read back from the local PostgreSQL store, not assumed: the two refused production sends land as REQUESTED + `DISPATCH_FAILED` and the development CONSOLE send lands as REQUESTED + DISPATCHED with `{"provider":"CONSOLE",…}`. Rate limiting, the 15-minute lockout, the 5-minute challenge retention after a failed send and the fail-closed behaviour on an unwritable record are unchanged — the fix moves a write, it does not soften a control. What this does **not** change: BLK-03 stays open, because the ordering fix makes the refusal visible rather than removing it.
- **Current Mitigation**: Test/Development environment supports deterministic fixture numbers and local auth tokens. Development `SMS_PROVIDER=CONSOLE` still dispatches to the console adapter (SMS-030 pins that the guard is production-only).
- **Remediation Procedure**:
  1. Register NABIN legal entity on telecom DLT portal (Vilpower / Jio / Airtel / Smartping).
  2. Register transactional SMS Sender ID (6-character header).
  3. Register transactional message templates with dynamic variable format:
     `"Your NABIN verification code is {#var#}. Valid for 5 minutes. Do not share this OTP."`
  4. Link approved DLT credentials in production backend `.env` (`backend/.env.production.example:74-79` is the template, and it matches what the code reads):
     - `SMS_PROVIDER=FAST2SMS` (or `TWILIO`) — **not** `SMS_GATEWAY_PROVIDER`, the name this register carried until 2026-10-12 and which no file in the repository reads (`src/services/SmsGatewayService.js:257` resolves `process.env.SMS_PROVIDER`). Following the old name would have produced a "configured" production that answers 503 on every login.
     - `DLT_ENTITY_ID=...`
     - `DLT_TEMPLATE_ID=...`
- **Estimated Lead Time**: 5–7 business days (external regulator approval).
- **Target Resolution**: **30 November 2026** (Milestone D).

## 4. BLK-07 DETAIL — LEDGER WRITE HONESTY (`#278`, `#280`, closed 2026-10-12 in the working tree and verified against a real PostgreSQL)

- **Severity**: MEDIUM as a release blocker (both swallows are fixed and guarded, and the fix is now proven on a live database); HIGH as a pre-launch risk, because a launch transaction that cannot be booked used to look booked.
- **Root cause, from source**: `LedgerRepository.recordDoubleEntry` read only one failure shape. supabase-js resolves a PostgreSQL refusal as `{ data, error }`, so every engine decision except the idempotency-key collision fell to a `console.warn` followed by a mirror `unshift` of an entry stamped `status: 'POSTED'`. `NabinDatabase.recordLedgerEntry` caught anything the repository did throw, warned, and mirrored a second time. `updateJobStatus` trusted that answer — and trusted the same way about the driver's earnings, which is the second half of the defect (`#280`): its `catch (e) { console.warn('⚠️ driverRepo.updateEarnings notice:', …) }` turned every deliberate refusal out of `DriverRepository.updateEarnings` (`DRIVER_NOT_FOUND`, `MONEY_OPERATION_IDENTITY_REQUIRED`, `DRIVER_NOT_DURABLE`, `IDEMPOTENCY_CONFLICT`, or the wallet store's own failure) into the offline-mirror answer `{duplicate:false, posted:false}`, after which the settlement booked the NET journal row the refused RPC never made, credited the cached wallet, counted the trip, debited the rider and returned COMPLETED. Its companion was a classification gap: `adjustWallet` answered a store refusal with a codeless, `storeFailure`-less `Error`, so even the path that did throw reached the route unclassifiable.
- **What changed**: refusals propagate through the platform's existing `storeFailure` → `replyStoreError` vocabulary (503 on an outage, 409 on a unique collision, 500 when the schema is not ready); a `23505` on either `journal_transactions` unique constraint answers `duplicate` and mirrors nothing; a refused `journal_lines` insert fails the posting; both settlement postings now happen before any in-memory counter moves; the earnings call is awaited with no `catch`, so a refusal aborts the settlement at that line; the wallet store failure throws `storeFailure('wallet adjustment', error)`; the capture path's ledger call is awaited; the completion and `verify-checkout` routes classify store failures instead of answering `409`/`400` with PostgreSQL's own sentence.
- **Evidence**: `backend/ledger_write_guard_test.js`, 32 checks (20 ledger + 12 settlement) **as of this 2026-10-12 record; the suite is 34 checks since `#264` added DEC-12/DEC-13 on 2026-10-13 — see the `#264` bullet below, which also de-pins DEC-09's `-500` expectation.** Ledger half: RED **6/18** before the fix, **20/20** after.
