# Customer re-edit queue - mapped to the screen ids the project stores

Authority: Stitch project `17214277447715826653`, 69 canonical screens, 37 of them conformant on both responsive axes as painted. This is the work order for the write pass. It was produced by reading back stored markup, headless-Chrome measurements and the content guard, and by no call that changes the project; the earlier version of this line said the project write quota was exhausted, and one answered design-mode write has since proved that no longer true.

Order is the owner's: 1 truth and content, 2 desktop or oversized canvases, 3 thin tablet layouts, 4 the remaining responsive failures, 5 visually weak. A slot appears once, in its highest band, and its directive already carries every lower band's demand, because `apply_r3e.directives()` builds one instruction per screen out of all the faults it measured. No slot lands in band 5 alone: a screen whose only fault is type size or touch-target size is not worth a re-ask, and that backlog is fixed by the redesign its band 1 to 4 entry already asks for.

That order is enforced, not only printed. `apply_r3e.py` sequences its run from this queue's own JSON, so band 1 writes before band 2 even though band 1 starts at slot 03 and band 2 at 01, and the shared runner no longer re-sorts a caller's list back into slot order. The same script makes no write call without `--go`: run bare, it prints the band sequence, the revision id each directive targets and its length, which is the guard against blindly regenerating all 65 screens. Before it writes it compares each slot's newest ledger claim with the `newest_stored_id` in this file and refuses on a difference, because a revision the round refused can still be the one the project stores; the recovery is to re-measure and republish this queue, not to override the check.

After a band writes, `reverify.py <slots>` re-measures those slots on all three axes - stored markup fetched by id, the same bytes painted at 390 and 768, and the content guard on that copy - and calls a slot PASS only when all three are clean. A screen that came back phone-sized but still prints an unseeded coupon code fails, which is the outcome the responsiveness-only version of that script used to report as a pass.

What the ledgers say about the frame itself, because it decides how a band has to be run. Across 155 design-mode answers this project has recorded, 101 passed the write gate, 29 came back on a desktop canvas over the cap, 12 were refused for copy the content guard caught, and 13 never returned a design at all (quota errors and blank renders). That is a 26% gate-refusal rate, and the same slot can land on either side of the split from one call to the next. `deviceType: MOBILE` is sent on every call and does not choose the frame, which is why the gate enforces the cap by refusing an answer rather than by trusting a parameter. Measured against each slot's newest persisted revision, 5 of the 69 screens are still over the cap (24, 25, 28, 31, 46). A refused answer is not withdrawn either: 41 of the 41 refusals became the revision the project stores anyway, which is why a round that fixed one axis can move a screen backwards on another and the queue has to be re-measured between attempts. Sometimes the refused render is the better artefact anyway, and the ledger holds the case: in `edit_state12.json` the slots 22, 24, 25, 30, 31, 53 each went in from a 780-pixel predecessor and came back at 2560, and every one of those refusals persisted - the owner adopted them because the copy they carried ended the fabrication each screen had been asked about, trading a canvas fault for a truth fault that can be repaired locally. So a desktop canvas should be expected to take more than one attempt, and the pre-flight compares the ledger chain with this queue because the project has moved on since either was read.

A directive answers three axes, because a screen can fail each of them independently: the responsive axes (the canvas the project stores and what Chrome painted from it), the truth axis (copy no backend route supports), and the brand axis (colour written as raw hex instead of the pinned tokens, a page weighted too heavily toward #1A3BA2, desktop furniture drawn into the markup). The brand axis is the one the responsive rules cannot see at all - a screen can pass both of them and still fail the owner's colour ruling - so every queued entry prints its `brand_flags` beside the sentence written to answer them.

## One promotion conflict the owner still needs to settle

The remediation brief names `FESTIVAL30` and `NABINFIRST50` as verified promotion examples. Read against the repository on 2026-10-04, the evidence runs the opposite way to how this document first stated it:

- **Seed.** `backend/src/database.js` seeds `NABINFIRST50`, `DELHIFOOD`, `AIRPORTDELHI` (lines 623, 646, 669) into its in-memory `this.promotions` array. `FESTIVAL30` is not a seed, and two of the three that are carry Delhi in their name - a separate owner question about which promotion a Mizoram customer should ever see.
- **Test suite.** `backend/test_suite.js` creates `FESTIVAL30` with `POST /api/admin/promotions` (`server.js:2640`) at line 392, asserts the creation at line 400, and redeems it on a ₹200 order through `POST /api/promotions/apply` (`server.js:2693`) at line 403 - so every run of the committed suite leaves an active `FESTIVAL30` behind. `createPromotion` (`database.js:3284`) writes through `promotionRepo` to PostgreSQL whenever that repository is connected.
- **Live dev database, read 2026-10-04.** The `promotions` table holds `FESTIVAL30` active (`ALL` service, `PERCENTAGE` 30.00, cap ₹90.00, minimum ₹100.00, valid to 2027-10-02, one per user) and holds none of the three seeded codes, among the 1996 rows the suites have accumulated. Checked with a read-only `select code, discount_type, discount_value, max_discount, min_order_amount, valid_until, is_active from promotions where upper(code) in (...)` against `supabase_db_nabin`; production was not queried.

So the content guard is truthful about the seeds and blind to the database: `audit_ride.py:COUPON_OK` whitelists `NABINFIRST50` alone - a code the mock layer carries and no live `promotions` row answers - while the code that faults is the one a test harness mints. Neither makes a design claim safe. The brief admits a coupon only on evidence that it is product data, and a row the suite re-creates on every run is fixture state, not an offer the customer app has decided to make. **Flagged, not applied:** nothing in this queue introduces `FESTIVAL30`, and the stored revisions already faulted for invented codes stay recorded as drift.

The owner decision is which code becomes product truth: seed a Mizoram-shaped promotion and point `COUPON_OK` at what the running database actually answers, or leave the fixture alone and keep the guard whitelisting the mock-layer seed. Until one of those is chosen the guard keeps faulting every code but `NABINFIRST50`, and no screen in this queue may show a coupon at all.
